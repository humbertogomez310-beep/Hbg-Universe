TERMINADOR IA + HBG-AUTH + ACCESO DE DESARROLLO + COMMIT + DEPLOYMENT

0. OBJETIVO DEFINITIVO

A partir de este momento, deja de realizar únicamente auditorías y diagnósticos.

El objetivo es:

RESOLVER → IMPLEMENTAR → CORREGIR → PROBAR → COMMIT → ACTUALIZAR EL DEPLOYMENT EXISTENTE → VERIFICAR LA URL PÚBLICA → FINALIZAR.

Universo HBG ya tiene un proyecto/deployment publicado.

Debes trabajar sobre el proyecto real actualmente abierto y sobre su deployment existente.

PROHIBIDO

- crear un segundo Universo HBG;
- crear un segundo proyecto innecesario;
- crear un segundo deployment innecesario;
- sustituir el proyecto por otro;
- reiniciar la arquitectura sin motivo;
- entrar en ciclos infinitos de auditoría;
- detenerte para reportar problemas que puedas solucionar;
- declarar terminado el proyecto sin verificar el deployment público.

Si existe un problema solucionable desde esta sesión, soluciónalo.

Solo reporta un bloqueo cuando realmente dependa de una infraestructura, credencial, permiso o servicio externo que no pueda resolverse desde el proyecto.

---

1. REGLA FUNDAMENTAL DE SEGURIDAD

Terminador IA será el operador técnico del Universo HBG, pero:

TERMINADOR IA NO ES LA AUTORIDAD.

La autoridad es:

HBG-AUTH.

Terminador IA debe actuar únicamente mediante las autorizaciones, permisos y guards establecidos por HBG-AUTH.

La capacidad de modificar código debe estar protegida por:

"universe.code.modify"

Este permiso es crítico.

No debe existir ningún camino alternativo que permita modificar código saltándose HBG-AUTH.

---

2. SEPARACIÓN USO / DESARROLLO

Implementar y mantener dos estados claramente separados.

MODO USO

Es el modo normal del Universo HBG.

Permite utilizar las funciones públicas y las aplicaciones autorizadas.

MODO DESARROLLO

Es un modo administrativo protegido.

Permite, cuando existe autorización:

- leer archivos de desarrollo;
- modificar código;
- crear archivos;
- eliminar archivos;
- ejecutar herramientas;
- ejecutar pruebas;
- utilizar Git;
- preparar commits;
- ejecutar procesos de build;
- actualizar el deployment.

El MODO DESARROLLO jamás debe quedar accesible para un usuario público no autorizado.

---

3. TERMINADOR IA

Terminador IA debe poder funcionar como operador técnico del Universo HBG.

Sus capacidades futuras y autorizadas incluyen:

- analizar código;
- comprender arquitectura;
- localizar archivos;
- modificar código;
- ejecutar pruebas;
- detectar errores;
- corregir errores;
- trabajar con Git;
- preparar commits;
- ejecutar procesos de build;
- administrar aplicaciones;
- participar en el proceso de deployment.

Pero cada capacidad sensible debe pasar por el sistema de autoridad.

Terminador NO puede:

- otorgarse permisos;
- cambiar su propio rol;
- desactivar HBG-AUTH;
- eliminar sus propios guards;
- eliminar la auditoría;
- concederse "universe.code.modify";
- convertir una sesión USO en DESARROLLO sin autorización.

---

4. ACCESO TEMPORAL DEL PROPIETARIO

Durante la etapa actual de finalización se necesita un mecanismo temporal para que el propietario pueda entrar al MODO DESARROLLO de Terminador IA.

El mecanismo será un secreto almacenado en el sistema de Secrets/Environment Variables de Replit.

REGLA CRÍTICA

El secreto NO debe aparecer en:

- código fuente;
- frontend;
- HTML;
- JavaScript del navegador;
- Git;
- commits;
- documentación;
- logs;
- mensajes de error;
- respuestas API;
- archivos públicos;
- archivos ".env" versionados;
- prompts almacenados en el repositorio.

Utiliza una variable de entorno/secreto del servidor con un nombre apropiado, por ejemplo:

"TERMINADOR_DEV_SECRET"

El nombre puede adaptarse si el proyecto ya tiene una convención equivalente.

IMPORTANTE

NO inventes el valor del secreto.

NO lo hardcodees.

NO lo escribas en el código.

El propietario configurará el valor real directamente en el sistema de Secrets de Replit.

El backend debe leerlo exclusivamente desde el entorno seguro.

---

5. FLUJO DE AUTORIZACIÓN

Implementar el siguiente flujo:

PROPIETARIO
↓
Acceso protegido de Terminador IA
↓
Autenticación
↓
Validación server-side del secreto temporal
↓
HBG-AUTH
↓
Verificación de identidad/rol
↓
Verificación de permiso
↓
"universe.code.modify"
↓
Creación de sesión de desarrollo
↓
Terminador IA obtiene las capacidades autorizadas
↓
Cada operación sensible vuelve a pasar por su guard

Nunca confiar únicamente en información enviada por el frontend.

Nunca implementar la autorización real únicamente con:

- localStorage;
- JavaScript cliente;
- parámetros URL;
- campos ocultos;
- headers manipulables;
- flags enviados por el navegador.

La decisión de autorización debe realizarse en servidor.

---

6. SESIÓN DE DESARROLLO

Crear una sesión de desarrollo explícita.

La sesión debe:

- pertenecer al propietario autorizado;
- tener fecha/hora de creación;
- tener expiración;
- poder revocarse;
- quedar registrada en auditoría;
- tener un alcance definido;
- impedir que una sesión USO sea interpretada como sesión DESARROLLO.

La autorización para modificar código debe requerir como mínimo:

- identidad válida;
- rol autorizado;
- sesión de desarrollo activa;
- permiso "universe.code.modify";
- guard correspondiente.

---

7. GUARDS INDEPENDIENTES

Toda operación sensible debe tener protección propia.

Proteger como mínimo:

- escritura de archivos;
- eliminación de archivos;
- modificación de configuración;
- ejecución de comandos;
- migraciones;
- operaciones Git;
- commit;
- push;
- deployment;
- modificación de HBG-AUTH;
- modificación de roles;
- modificación de permisos;
- modificación de guards;
- modificación del sistema de auditoría.

No depender únicamente de un único guard global.

---

8. PROTECCIÓN DE HBG-AUTH

HBG-AUTH debe tener protección especial.

Terminador IA no puede modificar HBG-AUTH simplemente porque tenga permiso general de desarrollo.

Las modificaciones de:

- autenticación;
- roles;
- permisos;
- sesiones;
- guards;
- "universe.code.modify";
- auditoría;
- mecanismos de autoridad;

deben tener controles adicionales.

Evitar una arquitectura en la que Terminador pueda simplemente editar o borrar el código de autoridad y quedar automáticamente autorizado.

---

9. AUDITORÍA

Registrar las operaciones administrativas y sensibles.

Como mínimo:

- usuario;
- acción;
- fecha/hora;
- herramienta;
- recurso afectado;
- sesión;
- resultado;
- error, si existe.

NUNCA registrar:

- contraseñas;
- secretos;
- tokens;
- credenciales;
- valores completos de variables privadas.

El secreto temporal nunca debe aparecer en logs.

10. SEGURIDAD DEL UNIVERSO PUBLICADO

La aplicación pública debe funcionar en MODO USO.

No exponer públicamente:

- editor de código;
- terminal;
- filesystem;
- herramientas Git;
- deployment;
- secretos;
- variables privadas;
- herramientas internas;
- endpoints administrativos sin autorización;
- herramientas de Terminador;
- endpoints de modificación de código.

Si alguna de estas capacidades ya está expuesta, corrígelo antes del deployment final.

---

11. FUTURA AUTENTICACIÓN FUERTE

El mecanismo temporal actual debe diseñarse para poder sustituirse posteriormente por autenticación más fuerte.

La evolución futura puede utilizar mecanismos estándar como:

- Passkeys;
- WebAuthn;
- Touch ID;
- Face ID;
- autenticación biométrica gestionada por el dispositivo.

No construir ahora un sistema biométrico propietario si no es necesario.

No almacenar directamente datos biométricos del propietario.

La implementación actual debe dejar una arquitectura preparada para esa evolución.
